QRun Blockchain Technology: Verified Capabilities and Research Tracks

QRun is an independently developed native Layer-1 research and engineering project. This guide inventories the capabilities that have source-level or test evidence, distinguishes candidate work from operational services, and identifies roadmap-only areas. It is not a claim that a production Mainnet or public Testnet is live.

Capability register

“Implemented candidate” means code exists in the engineering tree; “locally tested” means the named scope passed in a controlled local environment. Neither label implies independent audit, public deployment or production readiness.

Native ledger and transaction validation

Status: Implemented candidate; scoped tests. Rust-based ledger and transaction/state validation, block checks, candidate proof-of-work and difficulty adjustment, deterministic state commitments, supply-policy enforcement and chain-selection/reorganisation research.

History, persistence and recovery

Status: Candidate implementation; local recovery tests. Archive replay, snapshot validation, checkpoint/recovery models, persistent Anchor Vault creation and restart recovery, rollback safeguards and protected identity reload checks.

Authenticated peer networking

Status: Candidate implementation; controlled-network tests. Encrypted peer sessions, pinned identity research, bounded message handling, managed handshake workers, multi-source bootstrap agreement and fail-closed handling of inconsistent source histories. Current two-source end-to-end tests use loopback fixtures; public Internet reachability and independent operator convergence are not established.

Cryptographic verification

Status: Real verifier and selected test corpus. A Rust ML-DSA-65 verification adapter is tested against a selected hash-pinned 53-case external fixture (48 expected-valid and 5 expected-invalid). Hybrid Ed25519/ML-DSA-65 identity formats exist in candidate research paths. This does not make the entire chain quantum-resistant or prove full production-path activation.

Wallet and signed transactions

Status: Candidate tooling. A Windows native-wallet CLI and signed-transaction paths exist in the source. Public wallet interoperability, a live public balance and production-grade user key-management have not been established.

EVM and Solidity development

Status: Isolated lab; local validation. An EVM/revm laboratory and separate fixed-supply EVM test package cover contract execution, storage, gas, rollback, wallet-console and loopback-server behaviour. The EVM is not yet proven as canonical execution inside the native QRun state machine; the historical QX test asset is not native QZXB.

Market-operation processing

Status: Integrated local candidate; focused tests. Signed market-operation ingress, bounded durable pending-queue/journal handling, shared nonce coordination and replay/anchor validation are wired into the candidate service path. Acceptance means durably pending only—not mined, finalized, matched on an exchange or traded for real value. No public trading authorization exists.

AI-native application layer

Status: Design and roadmap. The project roadmap covers agent identity, owner-bounded payment authorization, verifiable job accounting, provider reputation and AI/compute coordination. Agent-payment policy is still design-stage; no production AI-agent payment service or live autonomous economic activity is claimed.

Latest scoped engineering evidence

  • Fresh-Genesis Anchor Vault creation and restart recovery tests passed locally, together with the focused Anchor Vault regression suite.
  • Protected Seed/Joining identity reload checks and a Release-node build passed in the maintainer environment.
  • The Joining configuration preparation path rejects missing or placeholder public Seed information, mismatched identity pins, unsafe listener addresses and unsafe storage placement in negative tests. No real public Joining configuration was generated because an externally verified Seed endpoint is not available.
  • Focused market/execution and node-launcher checks passed locally. These do not represent real-value trades or public market operation.
  • The selected ML-DSA-65 fixture has 53 cases; that number is a cryptographic fixture count, not a count of all project tests.

Only the listed scopes are claimed as passing. No aggregate all-target pass, independent audit or public-network soak is implied.

Ten public release safeguards

The ten safeguards on the release-status page are acceptance criteria, not a blueprint or disclosure of the project's private operational playbook. They summarize what must be independently demonstrated before a public network announcement. Detailed implementation and deployment material is intentionally not reproduced in this overview.

Source, review and reproducibility

The public default branch is a curated source and documentation baseline. Active engineering may continue on a separate candidate branch, and local work may not yet be published. A capability should be relied upon only after checking its exact source revision, test scope and release status.
