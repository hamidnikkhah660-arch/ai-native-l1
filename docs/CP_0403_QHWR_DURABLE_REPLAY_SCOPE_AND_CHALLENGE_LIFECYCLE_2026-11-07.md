# CP-0403 - QHWR Durable Replay Scope and Challenge Lifecycle

Date: 2026-11-07
Status: Engineering design contract; not an implementation, deployment approval, or security certification.
Parent: CP-0401 QHWR v1 protocol contract; CP-0402 fail-closed Noise dispatcher contract.
Working base: CP-0402 dispatcher branch at commit `87a9cb90c64256602c1608b6c501419276d7205c`.

## 1. Purpose

Define a replay-protection contract that is consistent with the actual QHWR v1 wire format and can later be implemented without weakening peer, network, operation, or expiry isolation. This document deliberately does not create a production ledger or claim anti-rollback guarantees.

CP-0402 remains unchanged. This work is on a separate stacked engineering branch. No listener, firewall, VPN/NetBird, DNS, route, Genesis, consensus, mint, public endpoint, or release-gate changes are authorized by this document.

## 2. Verified current protocol facts

1. QHWR v1 request bodies carry a 32-byte nonzero client-generated challenge. They do not carry `issued_at`, `expires_at`, a server-issued nonce token, or a server-verifiable expiry claim.
2. CP-0401 says the challenge is generated by the client CSPRNG and is unique among that client's outstanding operations.
3. The current READ dispatcher receives the authenticated Noise peer key and calls `reserve_once(peer, challenge)`. It does not pass the Network ID or operation to the ledger.
4. The Noise handshake does bind the configured Network ID in its prologue, but that fact is not currently represented in the replay-ledger API.
5. The dispatcher is READ-only today. COMPARE_AND_ADVANCE is rejected before provider, ledger, or signer side effects.
6. CP-0401/0402 require bounded, expiring replay state and durable reservation before provider or signer side effects.

## 3. Critical protocol gap: expiry cannot be inferred from v1

A server receiving only a client-generated random 32-byte value cannot determine when that value was created or when its intended validity ends. A client-supplied timestamp would be attacker-controlled unless authenticated and bounded by a trusted server policy. A first-seen timestamp is not an issuance timestamp and cannot prove that an old, delayed request is still fresh.

Therefore, adding `expires_at_unix_seconds` to the current ledger call without changing the challenge lifecycle would create a misleading API: it would timestamp server observation, not establish challenge freshness.

**Normative decision:** QHWR v1 challenge expiry MUST NOT be claimed or enforced by trusting client-provided time. The v1 ledger must retain consumed challenge tombstones for the full period in which the corresponding v1 request could be replayed. Since v1 defines no authenticated maximum request age, safe tombstone deletion for anti-replay purposes is not currently justified. Storage bounds must be enforced through admission quotas, per-peer rate limits, and capacity policy; capacity exhaustion fails closed. No silent eviction of unexpired/retained replay entries is permitted.

This limitation is a release blocker for unattended/production exposure of v1 unless a separately reviewed protocol rule establishes a finite replay horizon.

## 4. Required v1 replay scope

The durable uniqueness key MUST include all of:

- `network_id`: the exact 32-byte Network ID authenticated by the completed Noise prologue;
- `authenticated_peer`: the exact remote static public key returned by the authenticated Noise session;
- `operation`: a stable, explicitly encoded operation discriminator (`Read` or `CompareAndAdvance`);
- `challenge`: the exact 32-byte request challenge.

The dispatcher MUST pass the authenticated Network ID from the same Noise session context used for handshake verification, and MUST verify that it exactly matches the configured provider/network pin before touching the ledger, provider, or signer. Keep the dispatcher entry point private to the authenticated session-serving boundary; it MUST NOT accept a caller-supplied, unverified network identifier. Operation MUST be derived from the strictly decoded request, not from an independent caller argument.

Conceptual API shape (design only; not implemented):

```rust
pub struct QhwrReplayScope {
    pub network_id: [u8; 32],
    pub authenticated_peer: [u8; 32],
    pub operation: QhwrOperation,
}

pub trait QhwrDurableReplayLedger {
    type Error: fmt::Display;

    fn reserve_once(
        &mut self,
        scope: &QhwrReplayScope,
        challenge: &[u8; 32],
    ) -> Result<bool, Self::Error>;
}
```

The operation is part of the key even if the challenge bytes are identical. A challenge accepted for one network, peer, or operation MUST NOT implicitly consume or authorize the same bytes in another scope. Duplicate reservations within the same complete scope MUST have exactly one winner under concurrency.

## 5. Required v2 challenge lifecycle for bounded expiry

A future protocol version intended to support bounded expiry MUST use a server-issued challenge lease. The server creates a cryptographically random nonce and records it durably before returning it. The lease is bound to Network ID, authenticated peer identity, permitted operation, a unique lease identifier, and server-controlled issuance/expiry metadata.

Required flow:

1. Client establishes the pinned Noise session; the authenticated peer and Network ID are fixed for that session.
2. Client requests a challenge lease for one explicit operation.
3. Server authorizes that peer/operation, applies rate and outstanding-lease quotas, obtains time from an explicitly configured trusted clock, and generates a nonce using a CSPRNG.
4. Server durably records the lease as outstanding, with a bounded server-selected TTL and the complete scope, before sending the lease response.
5. Client returns the opaque lease token with the operation request. Client timestamps are never authoritative.
6. Server atomically transitions the exact lease from outstanding to consumed while validating scope and server time. Concurrent duplicates yield one successful consume only.
7. Provider and signer calls occur only after successful durable consume.
8. Expired outstanding leases are rejected. Consumed and expired records may be compacted only after a separately specified replay horizon and recovery/rollback model proves that no previously valid token can become acceptable again.

The lease token must be unforgeable and bound to the stored record (or authenticated by a server secret with explicit key rotation/recovery rules). A stateless MAC alone does not replace durable one-time consumption. Server restart, replica failover, backup restore, and clock rollback must not resurrect a consumed or expired lease.

The exact QHWR v2 message types, token encoding, TTL, clock-skew allowance, maximum outstanding leases, retention period, and key lifecycle are open design items. Do not guess constants in code before the threat model fixes them.

## 6. Time and expiry policy requirements (v2 only)

Before implementation, specify:

- authoritative time source and behavior when it is unavailable;
- maximum lease TTL and minimum/maximum accepted lifetime;
- whether expiry is exclusive (`now >= expires_at` is expired);
- allowed clock skew and how skew is bounded without extending validity indefinitely;
- monotonic-vs-wall-clock behavior across process and host restart;
- behavior on backward/forward clock jumps and clock rollback;
- retention/compaction horizon for consumed and expired leases;
- replica consistency and failover behavior;
- disaster recovery and stale snapshot/backup restore behavior.

If trusted time or durable lease state is unavailable or ambiguous, the server fails closed. It MUST NOT fall back to process memory, local mutexes, client time, or a best-effort clock.

## 7. Ledger correctness and security invariants

A qualifying implementation must prove:

1. Atomic uniqueness: exactly one concurrent reservation/consume succeeds for a given full scope and challenge/lease.
2. Scope isolation: changing any one of Network ID, peer identity, operation, or challenge changes the uniqueness domain.
3. Durability: acknowledged reservations survive process restart and host restart.
4. Replica safety: concurrent reservations across independently running replicas are linearizable.
5. Rollback safety: restoring stale snapshots/backups or rolling back the node host cannot make a consumed token acceptable again.
6. Fail-closed behavior: unavailable, corrupt, stale, or ambiguous ledger state causes rejection before provider or signer effects.
7. No eviction bypass: capacity pressure cannot silently remove a still-relevant replay record.
8. Bounded resource use: per-peer/global quotas and admission control prevent unbounded outstanding leases and uncontrolled storage growth.
9. Auditability: decisions can be audited without logging secret token material or private keys.

A database on the same host/volume as the node is not automatically an independent rollback domain. WAL, fsync, a local mutex, a second process, or a successful restart test alone does not prove cross-host anti-rollback.

## 8. Required qualification matrix

- duplicate request, same full scope;
- identical challenge across different Network IDs;
- identical challenge across different authenticated peers;
- identical challenge across READ and COMPARE_AND_ADVANCE;
- concurrent duplicate reservations in one process and across processes;
- concurrent duplicate reservations across replicas;
- expired, not-yet-valid, malformed, and boundary-time leases (v2);
- trusted clock unavailable and clock jumps/rollback (v2);
- ledger unavailable, corrupt, read-only, or ambiguous commit;
- crash before reservation, after durable reservation, and during response write;
- process restart and host restart;
- replica failover during and after reservation;
- stale snapshot restore, backup restore, and storage rollback;
- capacity exhaustion and quota enforcement;
- proof that rejected requests cause no Provider or Signer side effects.

Record each result separately as local unit test, local multi-process test, CI, independently administered multi-host qualification, or production evidence. Do not conflate these levels.

## 9. Implementation sequence

1. Review and approve this contract against CP-0401/0402; resolve the v1 retention limitation and v2 lease semantics.
2. Implement the v1 full-scope API without pretending it provides bounded expiry.
3. Add deterministic scope-isolation and concurrent-duplicate tests using a test-only ledger; do not label the test ledger production durable.
4. Specify QHWR v2 challenge-lease wire messages and trusted-time policy in a separate versioned contract.
5. Implement a durable, atomic, independently operated ledger behind the interface; qualify its consistency and rollback domain.
6. Integrate the v2 lease lifecycle only after protocol and ledger tests pass.
7. Keep CAS disabled until both the independent provider and replay ledger are qualified.
8. Obtain independent security and operational review before any production exposure.

## 10. Explicit non-claims and release gates

This document does not implement a durable ledger, challenge issuer, trusted clock, QHWR v2 codec, provider, signer, listener, deployment, or node-runtime integration. It does not prove linearizability, anti-rollback, cross-host durability, production readiness, Mainnet readiness, or full-network post-quantum security.

The current Noise profile remains classical X25519/ChaChaPoly. ML-DSA-65 response signatures do not make the complete network post-quantum.
