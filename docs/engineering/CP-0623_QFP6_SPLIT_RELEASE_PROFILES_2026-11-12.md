# CP-0623 — QFP6 split release profiles: permissionless base vs anchored extension

Status: engineering decision and implementation specification; candidate-only. No Mainnet authorization.

## Decision

QFP6 release qualification MUST distinguish two trust modes rather than impose one six-artifact checklist on every node:

- `permissionless_full_history`: ordinary nodes independently replay the complete chain from the immutable Genesis identity. Q6TS, Provider, Q6EA, and QAP1 are not universal base-protocol dependencies.
- `anchored_checkpoint`: an explicitly selected extension for checkpoint/pruned or anchored operation. It requires Q6TS authority signatures and independent monotonic trust-floor verification, plus the applicable Q6EA/Provider services and pins.

This preserves the permissionless design recorded in CP-0588 and CP-0590 while retaining the stronger trust requirements for the anchored mode.

## Manifest and validator changes required

Introduce a versioned `release_profile` discriminator. The validator must apply mode-specific requirements and reject ambiguous/missing profiles:

### permissionless_full_history

Required: canonical Q6CP, Q6GD, Q6PN, Genesis snapshot, independently pinned manifest/descriptor commitments, complete-history replay evidence, and qualified bootstrap/peer policy. Q6TS may be present as metadata but must not be represented as runtime-enforced or required for base-node startup.

### anchored_checkpoint

Required: all applicable base identity artifacts plus Q6TS trust envelope, independently pinned authority keyset, valid threshold signatures, exact network/profile/Genesis commitments, independently administered monotonic floor, and the Q6EA/Provider material required by the selected anchored workflow.

The validator must fail closed for missing required artifacts, profile mismatch, invalid hashes, or a claim that Q6TS is runtime-enforced when the selected executable does not enforce it. A package passing structural validation remains candidate-only and is not a Mainnet authorization.

## Acceptance tests

- Base profile validates its required artifact set without Q6TS and reports `q6ts_required=false`, `q6ts_runtime_enforced=false`.
- Anchored profile fails if Q6TS, independent authority pins, or trust-floor qualification are absent.
- Anchored profile rejects malformed, wrong-network, insufficient-threshold, revoked, expired, or stale/rolled-back Q6TS records through the existing Q6TS verifier path.
- Both profiles remain non-production unless independent consensus, cryptography, economics, peer/network, and operational reviews are complete.
- Existing Genesis 7B founder / 3B mining-ceiling invariants remain unchanged; no wallet key or Genesis signature is generated by package tooling.

## Scope boundary

This checkpoint specifies the correct split; it does not fabricate artifacts, configure external trust services, expose a listener, activate mining, or create liquidity. The next implementation should update the candidate manifest schema and validator to enforce these two profiles, then add focused tests.
