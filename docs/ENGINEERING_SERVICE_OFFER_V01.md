## Purpose

A small, evidence-driven engineering engagement for a team that needs a reproducible diagnosis, a focused Rust/protocol change, or an AI/ML experiment with testable acceptance criteria. This offer is designed around existing project evidence: locked/offline Rust builds, deterministic tests, cross-language vectors, state and serialization research, crash/recovery test harnesses, and AI/ML prototyping experience. Experimental QuantumZXB components are not represented as production-ready or independently audited.

## Package A — Rust / protocol reproducibility sprint

**Planning window:** up to five business days after a written scope is accepted, access and inputs are available, and the agreed start milestone is paid. A larger or ambiguous problem requires a separate written schedule; five days is a cap for the initial scoped sprint, not a promise to solve an undefined backlog.

**Suitable scope:** one bounded build/reproduction failure, serialization or state-transition defect, deterministic regression, CI/reproducibility gap, or a small protocol-integration question in one agreed repository.

**Deliverables:**

1. A short baseline note recording the reviewed commit, toolchain, exact reproduction command and current observed result.
2. A minimal reproduction or focused failing regression test, when the issue can be reproduced with supplied inputs.
3. One small patch/PR or an evidence-based root-cause report with recommended next change. A patch is included only when the cause and safe fix fit the signed scope.
4. A validation record listing commands, exit codes, relevant output, and any remaining warnings or blockers.
5. Handoff notes identifying changed files, assumptions, known limitations and suggested follow-up tests.

**Acceptance criteria (fixed in the scope statement before work starts):**

- The deliverable identifies an exact source revision and reproducible commands.
- Agreed tests run in the pinned or documented environment and their recorded result matches the claim.
- For a reproducible defect fix, the regression test demonstrates the prior failure and passes after the change; unrelated files and private data are not added.
- The final handoff clearly distinguishes verified behavior from untested assumptions and independent-review requirements.
- If a problem is not reproducible, depends on missing access, or exceeds the agreed scope, the deliverable is a diagnosis/status report rather than an invented fix; further work requires a written change request.

## Package B — AI/ML feasibility and reproducibility sprint

**Planning window:** up to five business days for one narrowly defined task, dataset or model workflow, subject to input availability and the agreed written scope.

**Deliverables:** a pinned environment, a runnable baseline, a small experiment script/notebook or minimal implementation, explicitly named evaluation metrics, observed results on the approved inputs, limitations and a handoff guide. Acceptance is based on running the named commands and reproducing the recorded metrics within agreed tolerances, not on a promised accuracy or business outcome. Private, personal or regulated data is excluded unless the client confirms a lawful processing basis and secure handling arrangement in writing.
