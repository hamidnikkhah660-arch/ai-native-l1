# CP-0392 — v0.4 Canonical Genesis Manifest Candidate

**Date:** 2026-10-24
**Status:** Candidate codec + independent deterministic vectors. Gate 2 and Gate 8 remain OPEN. No mainnet Genesis was activated and no production owner key is created by this work.

## Why this increment exists

The prior state-machine monetary candidate still has historical 4B founder / 3B miner / 3B public-goods parameters. A silent in-place change would break the existing policy fingerprint and snapshots. This increment introduces a separate v0.4 Genesis-manifest candidate with explicit version boundaries; it does not migrate or reinterpret old state.

## Manifest behavior

- Requires a non-zero network ID and an explicitly supplied owner-account identifier. No key is generated or stored.
- Binds format version, native protocol version 4, v0.4 policy fingerprint, eight-bucket initial accounting counters, initial state root and manifest hash. The root is derived from the existing deterministic account-ledger root, v0.4 policy, allocation-accounting commitment and zero cumulative miner issuance.
- Credits only 1,000,000,000 coins to the owner bucket in this candidate Genesis. Mining, airdrop, exchange/liquidity partnerships, marketing, developer/security, financial/strategic-supporter and burn-reserve budgets remain unissued at Genesis.
- Uses canonical fixed-width big-endian fields, rejects unsupported versions, non-canonical/truncated/trailing input, wrong policy, over-cap state and any initial allocation other than the prescribed owner credit.
- Has a Python independent vector generator at `simulations/quantumzxb_v04_genesis_vectors.py`; the Rust tests compare exact accounting bytes, fingerprint, state root, manifest bytes and hash with the shared fixture.

## Validation performed

- Five focused Rust tests cover Genesis round-trip/initial supply, zero IDs and unsupported versions, tamper rejection, determinism, network/owner domain separation, and exact equality with the independent Python golden vectors. CP-0393 adds a separate bridge test that materializes this manifest into the deterministic ledger and proves identical state roots.
- Independent Python-generated bytes and hashes are compared by the Rust test.
- This is a manifest/accounting candidate only. It is not yet the block producer/importer, complete ledger Genesis initializer, wallet/custody ceremony, state machine, PFM5 durable store, or production node runtime. The actual owner account must be reviewed and approved before any value-bearing Genesis could be constructed.

## Remaining Gate 2 work

1. Construct the real initial ledger/account state from this manifest and prove that its state root is exactly the manifest commitment.
2. Integrate the per-bucket accounting into signed allocation-release transitions, miner issuance, validation/import, fork choice/reorg rollback, durable persistence, snapshot/restart and replay.
3. Freeze production protocol parameters and block/transaction/consensus versions, create cross-language vectors for all transition paths, and audit every mint/credit call-site for cap bypasses.
4. Obtain an independent implementation/reviewer, reproducible release provenance, and no unresolved critical/high issues.

## Remaining Gate 8 work

The manifest does not provide anti-rollback. Gate 8 still requires an independently administered durable anchor with atomic provider-side CAS, pinned and separately managed receipt-signing keys, runtime integration, and multi-host/disk/VM-restore/crash/ambiguous-timeout qualification.

**Disposition:** This increases Gate 2 evidence but closes neither gate. Public value-bearing Mainnet and real-money trading remain NO-GO.
