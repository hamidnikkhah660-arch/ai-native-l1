# CP-0401 — PFM5 High-Water Noise RPC protocol contract

Status: design contract only; not a transport implementation, provider, deployment, or production approval.

## 1. Scope and dependency

CP-0401 specifies the application protocol that may later carry the CP-0400 authenticated High-Water request/response objects over the repository existing bounded DevnetNoiseSession stream. It is deliberately stacked on CP-0400 and does not change consensus, Genesis, transaction encoding, node admission, economics, wallet allocation, or public-launch gates.

The existing Noise profile is Noise_XX_25519_ChaChaPoly_SHA256. It provides a classical encrypted channel with operator-pinned static keys and a Network-ID-bound prologue. It is not post-quantum. The CP-0400 ML-DSA-65 response signature remains an independent application-layer authority proof; Noise authentication does not replace it.

## 2. Transport boundary

A connection must complete the existing Noise handshake and pass both sides configured static-key pins before any High-Water application message is accepted. The Noise prologue must bind the configured network identity. No plaintext fallback, alternate protocol fallback, or unauthenticated retry is permitted.

Each application message is exactly one Noise record. The Noise record existing 32-bit big-endian ciphertext length is the outer framing. The decrypted application payload is bounded to 8,192 bytes. Reject and close the session on truncation, oversized payload, unsupported version, malformed length, unknown operation, invalid status, trailing bytes, or invalid canonical encoding. Do not attempt to resynchronize after a malformed record.

The server must enforce handshake and record deadlines, connection concurrency limits, per-peer request budgets, and bounded outstanding-challenge state before public or unattended exposure. The existing Noise implementation has handshake/record deadlines and a bounded trusted-key set, but these controls do not by themselves constitute a complete public-service ingress policy.

## 3. Application message envelope

All integers are unsigned big-endian. All fixed-width identifiers and digests are 32 bytes. The envelope is:

| Field | Width | Rule |
|---|---:|---|
| magic | 4 | ASCII QHWR |
| version | 2 | 1 |
| message_type | 1 | 1 request, 2 response |
| operation | 1 | 1 READ, 2 COMPARE_AND_ADVANCE |
| body_length | 4 | exact number of following body bytes |
| body | variable | operation-specific; no trailing bytes |

The decoded total length must equal 12 + body_length and remain within the 8,192-byte payload bound. Unknown versions, message types, operations, and non-exact lengths fail closed.

## 4. Request bodies

### READ request

| Field | Width |
|---|---:|
| challenge | 32 |

The challenge must be nonzero, freshly generated by the client CSPRNG, and unique among the client outstanding operations. A response must echo it exactly.

### COMPARE_AND_ADVANCE request

| Field | Width |
|---|---:|
| challenge | 32 |
| expected_state_digest | 32 |
| next_state_length | 4 |
| next_state_wire | exact CP-0400 QHWA v1 encoding |

The next_state_length must equal the exact QHWA v1 fixed width of 414 bytes (4-byte magic + 2-byte version + four 32-byte identity fields + 8-byte journal sequence + 8-byte record generation + eight 32-byte record fields + 8-byte object generation). The server must decode and validate the canonical QHWA bytes against its configured authority/provider/network/Genesis identity before considering a write. The challenge must be nonzero and unused for the lifetime of the connection/request window.

The server must not trust client-supplied identity fields, key identifiers, or signatures as authorization to mutate state. Authorization is derived from the mutually pinned Noise peer identity plus server-side policy, and the server independently validates the state transition.

## 5. Response bodies

A successful READ or COMPARE_AND_ADVANCE response carries the exact CP-0400 signed-response object, encoded as:

| Field | Width |
|---|---:|
| challenge | 32 |
| key_id | 32 |
| key_generation | 8 |
| wire_state_length | 4 |
| wire_state | exact QHWA v1 bytes |
| signature_length | 4 |
| ML-DSA-65 signature | exact configured algorithm width |

The wire_state is exactly 414 bytes and the ML-DSA-65 signature is exactly 3,309 bytes (the repository configured FIPS 204 ML-DSA-65 signature width). The response must echo the request challenge. The signature is the CP-0400 response-signing digest over its domain separator, challenge, key ID, key generation, encoded-state length, and exact canonical state bytes. The client verifies the pinned authority key, key ID/generation, authority/provider/network/Genesis bindings, canonical state, challenge, and ML-DSA-65 signature before exposing state to the coordinator.

An error response carries a fixed status code and no state or signature. Initial status assignments: 1 malformed request, 2 unsupported version/operation, 3 unauthorized peer, 4 challenge replay/expired challenge, 5 state conflict, 6 invalid transition, 7 provider unavailable, 8 durable commit outcome unknown. Error responses are diagnostic only and never authorize state changes. Unknown status values fail closed. The server must not disclose secrets, private keys, storage paths, or internal exception strings.

## 6. Atomic provider contract

The network service is not itself the source of monotonicity. It delegates to a separately operated provider interface with these semantics:

1. read returns the currently committed canonical state.
2. compare_and_advance(expected_digest, next_state) is one linearizable conditional transaction: compare the complete current canonical state digest and replace it with the complete next state as one atomic operation.
3. The server validates the legal one-step journal-sequence advance and the CP-0400 Prepared/Finalized transition rules before calling the provider.
4. A successful response is signed only after the provider confirms durable commit and a fresh readback equals the exact requested successor.
5. A stale expected digest returns conflict and cannot overwrite the winner.
6. If the storage result is ambiguous, the server performs a fresh provider read. Exact successor means committed; exact predecessor means not committed/retryable; any other state means conflict/unknown and must fail closed.
7. Durability must survive process restart and host restart. A local file, local database, or second process on the same rollback domain does not establish an independent anti-rollback authority.

The provider atomicity and durability are not supplied by Noise, ML-DSA-65, the client adapter, or this protocol envelope. They require a separately qualified backend and independent rollback domain.

## 7. Replay, retry, and concurrency

The server maintains bounded, expiring outstanding-challenge/replay state scoped to the authenticated peer and connection policy. A challenge is consumed exactly once when a request is accepted; duplicate or expired challenges are rejected. Restart behavior must be explicit: because a process-local replay cache is lost on restart, the server must either persist replay protection in the authority domain or require a fresh authenticated session and use a durable request ledger before accepting state-changing operations. The latter is required for production consideration.

A client never retries a state-changing request blindly after a timeout. It performs a fresh READ with a new challenge and classifies the observed state against the exact predecessor and successor. Competing writers are resolved only by the provider atomic compare-and-advance; client-side locks are not sufficient.

## 8. Required implementation and qualification sequence

1. Implement strict envelope codecs with boundary, truncation, trailing-byte, unknown-version, and maximum-size tests.
2. Implement a client transport over an established Noise session; preserve the CP-0400 adapter signature verification and fresh challenge behavior.
3. Implement a server dispatcher with explicit peer authorization, bounded request/replay state, and no implicit public listener.
4. Implement the server-side signing interface without placing private signing keys in the node or ordinary provider state database.
5. Implement or connect a genuinely independent atomic durable provider; do not present a local file backend as anti-rollback protection.
6. Test two concurrent writers, duplicate/replayed challenges, wrong peer/network, tampered signatures, response loss after commit, provider crash before/after durable commit, process restart, host restart, stale backup restore, and disk rollback.
7. Qualify on two independently administered hosts and obtain independent cryptographic and operational review.

## 9. Explicit non-goals and release gates

This document does not implement a TCP client/server, server signer, durable provider, replay ledger, key provisioning/rotation/revocation, public service, cloud resource, or runtime/node integration. It does not prove cross-host availability, linearizability, anti-rollback, production key custody, Mainnet readiness, or full-network post-quantum security. The existing Noise channel remains classical X25519/ChaChaPoly.

Any future listener must be opt-in, bind only to an explicitly configured private interface by default, and remain disabled in public/mainnet profiles until independent review and multi-host qualification. No firewall, VPN, NetBird, DNS, route, Genesis, consensus, or release-gate changes are authorized by this contract.
