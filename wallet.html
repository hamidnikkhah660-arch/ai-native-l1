QZXB Native Wallet: Current Capabilities and Safety

The repository contains a Windows-native QZXB wallet CLI candidate for local account creation, recovery, address inspection and signed TXN2 transfer construction. It is not yet a released public Mainnet wallet, mobile app, hardware-wallet integration or a Trust Wallet listing.

Do not deposit funds or share a recovery phrase. QRun has no value-bearing public Mainnet or independently verified spendable public QZXB balance. A successful local wallet command does not create a public coin balance. Never paste a mnemonic, seed, private key or wallet file into chat, a website form or an untrusted application.

What the candidate CLI supports

Create and recover

Create a standard 12-word English BIP39 recovery phrase or restore from a valid 12-word phrase. Console entry for restoration is masked. The wallet derives a QZXB-specific Ed25519 signing seed from the BIP39 seed.

Local custody

The QZKW1_Windows_CurrentUser_DPAPI format protects the 32-byte signing seed using Windows CurrentUser DPAPI. This is desktop-user protection, not an HSM, hardware wallet or portable encrypted backup.

Address and signing

Inspect the public account identifier and construct signed native TXN2 transfers. The default self-contained signature mode carries the public key with an Ed25519 signature so validating nodes can derive and check the sender account.

Read-only queries

RPC status, balance and transaction-status queries are restricted by the candidate client to numeric loopback addresses and require a read-only RPC response.

Recovery and compatibility

The candidate recovery path uses a 12-word English BIP39 phrase, then applies the QZXB-specific domain QUANTUMZXB-ED25519-SEED-FROM-BIP39-V1 before deriving the Ed25519 key. This is not a standard Bitcoin/EVM BIP32 derivation path. A generic wallet that accepts the same BIP39 words will not necessarily derive the same QZXB account.

The DPAPI-protected wallet file is tied to the Windows CurrentUser protection context. For a new Windows user or machine, the documented restore path creates a new protected file from the recovery phrase; the DPAPI file alone is not a portable cross-device backup.

Trust Wallet, MetaMask, Ledger, Trezor, WalletConnect, mobile apps and browser extensions are not currently qualified as native QZXB wallet integrations. Adding a custom EVM network does not add support for the QRun native protocol or its chain-specific Ed25519 derivation. Do not import the QZXB phrase into an unsupported wallet to experiment.

Native transfer flow and confirmation limits

  1. The sender constructs and signs a TXN2 transfer with the intended network ID, recipient account ID, nonce, amount, fee and expiry.
  2. An optional --submit-to path sends the signed transaction using the versioned QZTS/1 transaction-ingress protocol.
  3. The node admission acknowledgement means only that the candidate ingress accepted the transaction to its mempool. It does not prove block inclusion, canonical confirmation, finality, a public balance or settlement with a buyer.

The current candidate RPC query surface is loopback-only. The wallet CLI source is part of PR #135 on a separate feature branch; that PR remains Draft and is not a production binary release.

Native QZXB and EVM test assets are separate

The separate QX ERC-20 test asset and browser deployment console use EVM test/local environments. They are not the native QZXB coin, not a QRun-to-EVM bridge, and not a source of native QZXB/USDT liquidity. No cross-chain transfer route is currently claimed.

Review and next wallet milestones

  • Freeze the production QRun network/Genesis identity and align the QFP6 candidate with owner policy CP-0566D.
  • Qualify wallet create/restore and signed transfers against independent nodes on the same production identity, including inclusion, confirmation, reorg and recovery tests.
  • Define and review the chain-specific wallet integration package before claiming third-party, mobile or hardware-wallet compatibility.
  • Publish reproducible wallet binaries and checksums only with a reviewed network release and clear custody/recovery instructions.
